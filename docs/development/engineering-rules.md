# 工程规则

本文档保存全仓库开发时长期有效的做事方式。产品范围、系统边界和接口行为分别由
`specs/`、`docs/architecture/` 和 `docs/contracts/` 负责，不在这里重复。

## 修改原则

- 先理解相关代码、调用关系、类型、测试和已有约定，再修改。
- 优先修复根本原因。需要兼容或降级时，把它设计成明确、可观察、可测试的产品行为。
- 业务边界围绕真实能力形成；跨边界只依赖公开接口，不依赖对方内部文件结构。
- 不强制套用固定的 `domains/features` 目录模板，也不提前规定状态管理层级。
- 新抽象、package 和共享模块必须有明确职责、使用者和变化原因。名称不是判断标准；
  没有负责人和边界的杂物模块才是问题。
- 文件是否拆分由职责、变化原因、可测试性和评审难度决定，行数只作为提醒。

## TypeScript 和状态

- 新代码使用严格 TypeScript 配置，`any` 默认由 lint 拒绝。确实无法用 `unknown`、
  泛型或准确类型表达时，只允许局部例外并说明原因。
- 优先使用类型收窄、type guard、`satisfies` 和运行时 schema。类型断言不能代替对
  外部输入的校验，也不能使用双重断言逃避类型系统。
- 状态放在能够唯一拥有它的最窄边界；可推导的数据不重复保存。只有生命周期和多个
  独立使用者确实需要时，才把状态提升到更高层。
- UI 负责展示、交互和状态连接；可独立测试的业务规则与数据转换留在所属业务边界。

## 注释、日志和测试

- 注释使用中文解释原因、约束、安全边界和容易被误改的特殊行为，不复述代码字面含义。
- 日志说明执行位置、关键输入、状态、分支原因和异常上下文；不记录 Secret、真实用户
  内容或不必要的绝对路径。定位完成后决定保留、降级或删除调试日志。
- 业务规则和状态转换优先使用单元测试；DSH、Core、插件和权限边界使用契约或集成
  测试；最重要的用户流程使用少量端到端测试。
- 不为覆盖率数字编写 README、样式、配置或大规模 UI snapshot 测试。安全边界必须
  覆盖拒绝路径。

## 工作区和外部动作

- 默认只在当前 Git worktree 解析后的根目录内工作。仓库外资源只有在当前任务明确
  授权后才能访问；迁移输入默认只读。
- 保留未知和未提交的工作区状态。使用范围明确的 status、diff 和增量编辑，不使用
  reset、clean 或大范围 restore/checkout 丢弃无关修改。
- 本地编辑和测试不授权外部写操作。Push、PR 修改、tag、release、publish、签名、
  GitHub 设置或 Secret 修改、特权 workflow、真实数据迁移和生产切换都需要针对该
  动作的明确授权。
- Workflow 使用最小权限，第三方 Action 固定到完整 commit SHA。编写 workflow 不等于
  获得发布、部署或迁移权限。

## 数据和生成物

- 测试优先使用虚构数据。脱敏 fixture 必须记录来源、字段处理方式和评审结果。
- 浏览器状态、Cookie、登录数据、API key、证书、真实剪贴板、Session 内容和用户文件
  不进入仓库。
- 本地 cache、临时文件和生成证据放在已忽略的 `.hermit/`。外部 DSH 资格认证源码
  使用明确授权的只读缓存，不嵌套进本仓库。
- Symlink、junction 和等价链接解析后必须留在已授权范围内。

## 文档

- 第一方维护性 Markdown 使用简体中文，中文版本是唯一权威来源。正式标识符、命令、
  API/schema key、文件路径和第三方原文保持原文。
- 需要英文入口时使用带 `translation-of` 声明的派生翻译；翻译不能增加规范事实。
- 文档只记录当前有效事实。历史信息仅在仍影响迁移、兼容、来源追溯或回滚时保留在
  对应 `migration/`、change-specific `specs/` 或 provenance 中。
- 只有本次改动会让权威文档错误、过时或误导时才更新文档。不要为了目录完整创建
  README、ADR 或 scoped `AGENTS.md` 空壳。
- 调研资料用于追溯理由，不负责规定当前行为；正式结论必须写入需求、架构或契约。
