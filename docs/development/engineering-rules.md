# 工程规则

本文档保存全仓库开发时长期有效的做事方式。产品范围、系统边界和接口行为分别由
`specs/`、`docs/architecture/` 和 `docs/contracts/` 负责，不在这里重复。

## 修改原则

- 先理解相关代码、调用关系、类型、测试和已有约定，再修改。
- 优先修复根本原因。需要兼容或降级时，把它设计成明确、可观察、可测试的产品行为。
- 业务边界围绕真实能力形成；跨边界只依赖公开接口，不依赖对方内部文件结构。
- 不强制套用固定的 `domains/features` 目录模板，也不提前规定状态管理层级。
- 新抽象、package 和共享模块必须有明确职责、使用者和变化原因。名称不是判断标准；
  没有负责人和边界的杂物模块才是问题。
- 文件是否拆分由职责、变化原因、可测试性和评审难度决定，行数只作为提醒。
- 新增跨边界能力、基础设施、第三方依赖或明显维护成本的自研实现前，先核对仓库现有
  契约和实现是否已经覆盖；涉及外部 API、平台能力或复杂依赖时，优先查阅官方资料和
  成熟实现。

## TypeScript 和状态

- 新代码使用严格 TypeScript 配置，`any` 默认由 lint 拒绝。确实无法用 `unknown`、
  泛型或准确类型表达时，只允许局部例外并说明原因。
- 优先使用类型收窄、type guard、`satisfies` 和运行时 schema。类型断言不能代替对
  外部输入的校验，也不能使用双重断言逃避类型系统。
- 同一业务 vocabulary、状态集合或固定选项在类型、运行时校验、UI 选项、RPC 或持久化
  序列化中使用时，应维护一个 canonical source，并从它派生其他表示，避免多份值表漂移。
- 状态放在能够唯一拥有它的最窄边界；可推导的数据不重复保存。只有生命周期和多个
  独立使用者确实需要时，才把状态提升到更高层。
- UI 负责展示、交互和状态连接；可独立测试的业务规则与数据转换留在所属业务边界。

## 注释、日志和测试

- 注释使用简体中文，重点说明名称、类型和代码结构无法充分表达的业务语义、设计原因、
  不变量、生命周期、安全边界和外部契约限制。
- 变量、方法、接口字段和类型定义应根据其职责补充中文注释；注释必须提供额外语义，
  不得机械重复名称、类型或代码字面含义。
- 导出的 public contract、跨 package API、RPC、schema 和持久化 domain model，必须说明
  类型整体语义，并逐项说明字段含义、身份稳定性、单位、可空性、生命周期或兼容约束。
- 涉及 Canonical 状态、外部输入、revision、generation、token、lease、异步完成、资源
  释放、权限、安全、可信边界、幂等、取消、超时、重试、缓存或 projection 的变量和方法，
  必须说明其用途及有效性约束。
- 导出函数、异步函数、有副作用的函数、生命周期函数以及包含非显然业务规则的方法，
  必须说明职责和必要的失败、取消或状态约束。
- 简单局部变量、直接映射和显然的 JSX 不得添加只有“获取 X”“X 列表”“点击事件”等
  信息增量很低的注释；确有语义差异时，应说明差异和原因。
- 注释必须与当前代码和契约保持一致；发现注释与实现不一致时，应同步修正，不能保留
  误导性说明。
- 日志说明执行位置、关键输入、状态、分支原因和异常上下文；不记录 Secret、真实用户
  内容或不必要的绝对路径。定位完成后决定保留、降级或删除调试日志。
- 业务规则和状态转换优先使用单元测试；DSH、Core、插件和权限边界使用契约或集成
  测试；最重要的用户流程使用少量端到端测试。
- 不为覆盖率数字编写 README、样式、配置或大规模 UI snapshot 测试。安全边界必须
  覆盖拒绝路径。

## 异常与预期失败

- 每个边界都必须区分成功、预期失败和程序异常；取消、超时、权限拒绝、旧 revision、
  重复调用、可选能力缺失等预期结果使用契约规定的 typed result 或 error 表达。
- 真正违反不变量、无法恢复或需要上层决定的程序异常可以抛出；不得无日志、无状态转换、
  无返回值地静默吞掉异常。只有明确设计为可忽略的情况才允许消费错误，并说明原因。

## 工作区和外部动作

- 默认只在当前 Git worktree 解析后的根目录内工作。仓库外资源只有在当前任务明确
  授权后才能访问；迁移输入默认只读。
- 保留未知和未提交的工作区状态。使用范围明确的 status、diff 和增量编辑，不使用
  reset、clean 或大范围 restore/checkout 丢弃无关修改。
- 本地编辑和测试不授权外部写操作。Push、PR 修改、tag、release、publish、签名、
  GitHub 设置或 Secret 修改、特权 workflow、真实数据迁移和生产切换都需要针对该
  动作的明确授权。
- Workflow 使用最小权限，第三方 Action 固定到完整 commit SHA。编写 workflow 不等于
  获得发布、部署或迁移权限。

## 数据和生成物

- 测试优先使用虚构数据。脱敏 fixture 必须记录来源、字段处理方式和评审结果。
- 浏览器状态、Cookie、登录数据、API key、证书、真实剪贴板、Session 内容和用户文件
  不进入仓库。
- 本地 cache、临时文件和生成证据放在已忽略的 `.hermit/`。外部 DSH 资格认证源码
  使用明确授权的只读缓存，不嵌套进本仓库。
- Symlink、junction 和等价链接解析后必须留在已授权范围内。

## 版本与平台证据

- 长期开发和兼容政策使用经过验证的版本范围，不用某个补丁版本替代兼容性结论。
- lockfile、运行时 manifest、SBOM 和验收报告记录某次候选实际解析的精确版本；RC、已知
  互操作约束和外部 fixture provenance 可以精确固定。
- “本机观察到能启动”不等于“项目已验证”。工具链按项目已验证、候选、诊断可用和实验线
  分级；只有项目已验证组合可以生成资格证据。
- `package.json#engines` 表达仓库脚本可以进入的宽兼容范围，不承担发布资格门；
  `verify:toolchain` 和原生打包入口才负责强制项目已验证组合。
- 桌面发布物必须在目标操作系统和架构的原生 runner 上打包、启动和退出。跨平台生成的
  文件不能替代原生进程、安装器、签名、公证、关机和权限行为证据。

## 文档

- 第一方维护性 Markdown 使用简体中文，中文版本是唯一权威来源。正式标识符、命令、
  API/schema key、文件路径和第三方原文保持原文。
- 需要英文入口时使用带 `translation-of` 声明的派生翻译；翻译不能增加规范事实。
- 文档只记录当前有效事实。历史信息仅在仍影响迁移、兼容、来源追溯或回滚时保留在
  对应 `migration/`、change-specific `specs/` 或 provenance 中。
- 只有本次改动会让权威文档错误、过时或误导时才更新文档。不要为了目录完整创建
  README、ADR 或 scoped `AGENTS.md` 空壳。
- 调研资料用于追溯理由，不负责规定当前行为；正式结论必须写入需求、架构或契约。
- 文档权威入口是 `docs/document-authority.yaml`。它只登记“某类事实去哪篇文档找”，
  不复制产品事实；修改架构、契约、需求或 M1 时，先更新对应 authority，再同步引用。
- `docs/provenance/deepseek-harness/snapshots/` 是按上游 commit 冻结的外部原文，不参加
  第一方中文、翻译和相对链接门禁；版本、文件摘要和 runtime 对齐由
  `verify:dsh-upstream` 专项校验。
- `docs/architecture/system-boundaries.md` 是当前系统职责、依赖方向和生命周期模型的
  唯一权威；`docs/contracts/` 只写边界义务；`specs/` 只写需求和阶段验收；`docs/adr/`
  只写重要决定及其原因；旧 ADR 只能通过新 ADR supersede，不能改写历史正文。
- 文档治理检查只验证索引、链接、状态和旧方案污染，不用不稳定的语义重复检测替代评审。
